### 2026-08-21 · 研究候选先对照仓库实际结构再立项
- 情境：第二轮研究 MCP 安全与性能时，按 AGENTS.md 的简化包列表推断 `guard/compaction/skill` 不存在，实际仓库含 50+ 包（mcp-client、repeat-tool-reminder、compaction-tool-result-pruner 均已实现）。
- 教训：写 BACKLOG 条目前必须 grep/read 现有实现核对机制是否已存在——本轮 arXiv 的 doom-loop 指纹检测（已被 guard repeat-tool-reminder 覆盖且更优）与工具输出 offload（已被 compaction-tool-result-pruner 覆盖）若直接立项就是重复工作。
- 适用：所有研究→评估环节；不适用于全新领域（无对应包）的探索性立项。

### 2026-08-21 · 在途大功能会阻塞多轮落地，研究模式产出仍有价值
- 情境：web bind-address 功能连续两轮（36 文件在途）使工作区变脏，完整模式无法启动，代码落地连续挂零。
- 教训：不要在「等工作区干净」上空转；研究模式的 BACKLOG 评估、现状核对、发布链路验证（fork→evolve/state→PR）本身就是可审查产出，应尽早打通状态 PR 以获得每日可见交付。
- 适用：进化循环调度与优先级判断；不适用于紧急安全修复（应直接提请人工处理）。

### 2026-08-21 · 无人值守自动化环境限制会话内工具
- 情境：本轮 `todo_write` 被无人值守自动化允许列表拒绝，进度追踪工具不可用。
- 教训：自动化会话把进度与结论全部落到磁盘状态文件（RUNLOG/BACKLOG），不依赖会话内 todo 工具；工具失败不代表任务失败，改用协议内途径（状态文件+git）继续。
- 适用：每日定时自动化会话；不适用于交互式会话（可用完整工具集）。

### 2026-08-22 · 漂移数以 fetch 后实测为准，禁止沿用旧值
- 情境：第三轮沿用上轮记录的「落后 536 提交」，`git fetch origin` 后实测为 743（origin 已推进到 dsh-v0.1.1-rc.2）。
- 教训：与上游漂移是时效性数据，每轮必须 fetch 后 `git rev-list --count HEAD..origin/master` 重新实测并写入 STATE 统计；在途大功能拖得越久，基线过期成本越高（536→743 两轮间扩大 39%）。
- 适用：所有涉及与上游同步的轮次；不适用于工作区干净且当日 fetch 过的轮次（可引用当日实测值）。

### 2026-08-22 · 收尾前核对进化目录无残留，修订集中在提交前完成
- 情境：第三轮发现第二轮遗留 SKILL.md/STATE.md 的协议修订（--no-verify、凭据预检、PR 被拒处理）未提交，混入下一轮状态提交。
- 教训：状态文件修订应在提交前一次性完成；发布前 `git status --porcelain` 核对两个进化路径无残留，避免跨轮混杂与「提交≠工作树」的歧义。
- 适用：状态发布链路（每轮收尾）；不适用于完整模式的代码落地（代码改动走独立提交）。

### 2026-08-22 · 网络不可达时漂移处置：沿用实测值并显式注明「未实测」
- 情境：第四轮 `git fetch origin` 因 github.com:443 连接失败未更新 origin ref；若沿用旧值但不注明，后续轮次会把「沿用值」误当「实测值」。
- 教训：fetch 失败不阻塞流程——漂移沿用最近一次实测值并在 STATE 统计与 RUNLOG 显式标注「未实测/沿用」；推送失败则把重推命令写入待人工决策区；网络层失败与 git/权限失败要区分记录，避免下轮误判为 PR 权限问题。
- 适用：所有依赖 github 网络的轮次（fetch/push/gh pr）；不适用于工作区干净且网络正常时的完整模式轮次（正常 fetch 实测）。

### 2026-08-22 · 缺口核验要精确到「层级」，同名词不同层不算已覆盖
- 情境：第四轮立项 015（工具瞬时失败重试）时先 grep 到 `llm-retry`，差点误判「重试已实现」；实际 llm-retry 只覆盖模型请求层，工具执行层（guard timeout-policy 注释预留的 retry 接缝）是真空缺。016 同理：agent-loop 的 maxTokens 是单请求输出上限，不是会话级预算。
- 教训：外部 best practice 提出的能力，核验时先确定它在仓库里的准确层级（模型请求/工具执行/会话预算…），再判断该层是否已覆盖；把「同名词但不同层」的实现列出来并写明其边界，缺口结论才可靠。
- 适用：研究→评估立项（防重复立项）；不适用于完全空白领域的新立项（无同名词可混淆）。

### 2026-08-22 · 自进化循环的评估器必须外置（Weng 2026-07-04 Harness Engineering for Self-Improvement）
- 情境：第四轮研究自进化 harness 文献，Self-Harness（propose-evaluate-accept）与 AHE（可观测性：每个失败定位组件、每个编辑有证据）都指向同一安全结论——进化循环优化什么就会过拟合什么，评估器与权限控制必须在循环之外。
- 教训：本循环的门禁命令（typecheck/lint/build/test）、待人工决策区、受保护路径授权都是「外置评估器」的落实，任何进化产物（代码/状态/技能）都不能给自己签发通过；同时把「弱点评测先行」写进 SKILL.md 研究节（选题从门禁失败/自愈事件挖掘，而非纯轮换）。
- 适用：设计任何 self-improving 循环（技能/协议/代码进化）；不适用于一次性人工驱动的常规开发（无需自进化护栏）。

### 2026-08-24 · 同文件信任边界防御不均 = 高置信弱点信号
- 情境：第五轮审计 009 时发现 `packages/mcp/mcp-client/src/tools.ts` 对工具返回值侧（extractText/decodeImage/projectContent）防御极其严谨，多处明确标注 network trust boundary，唯独 `tool.description` 透传（L166）无任何防护。
- 教训：「代码作者已意识到某边界、但漏掉边界上一处入口」比「完全没意识到边界」更说明是真缺口而非设计取舍——防御性代码的存在本身就是信任模型的证据。审计时先看同文件/同模块其他信任边界如何处理，失衡处即高置信落点。
- 适用：安全类审计与立项；不适用于纯功能性研究（无信任边界可对照）。

### 2026-08-24 · 外部权威与本地代码双证据链确认缺口后再落地
- 情境：009/010 的缺口被 OWASP MCP Top 10（MCP06）、Christian Schneider「Securing MCP: defense-first」、imti.co 三处独立外部权威确认，且本地代码失衡证据精确到行号；本轮据此把审计结论从「待核验」升级为「缺口确认」。
- 教训：单一来源的 best practice 只是候选；外部权威（行业标准/独立作者）+ 本地代码实证（行级证据）双链闭合时，条目才从 idea 级升为可评审的落地提案。审计报告应同时给出外部链接与本地行号，方便人工评审快速决策。
- 适用：安全加固条目的评估升级；不适用于流程/协议类进程改进（本地自证即可）。

### 2026-08-24 · 评估落地形态时提前映射受保护路径
- 情境：010 的社区推荐落地形态是「描述变更时 re-prompt 用户」（Christian Schneider），但 re-prompt 落点会触及 `packages/interaction/`（受保护路径）；评估时识别并在待人工决策区标注，避免落地阶段才撞护栏。
- 教训：外部 best practice 推荐的「完整形态」常落在受保护能力（interaction/guard/session/credentials）上；评估时要把推荐形态拆成「最小安全子集」（如仅记录变更日志）与「完整形态」（re-prompt），分别标注权限边界，给人工决策留出选项。
- 适用：所有安全类条目的评估与立项；不适用于无受保护路径交集的纯效率改进。

### 2026-08-24 · 漂移可能被人工干预清零，每轮实测并记录原因
- 情境：第六轮 fetch 后发现本地落后 743 已归零——人工于 2026-08-24 10:59 把 origin/master merge 进本地 master（commit 89ed947a41）；若沿用上轮「落后 743」会把已同步误判为未同步。
- 教训：漂移数每轮 fetch 后实测并与上轮对比；值突然变化时查 reflog/log 定位原因（merge/rebase/人工操作），把「归零 + 原因（merge commit）」而非数字本身写进 STATE/RUNLOG；同时注意 merge 后未提交的在途改动叠加在新基线上，收尾有冲突风险。
- 适用：所有与上游同步统计的轮次；不适用于 fetch 失败且确认 origin ref 未更新的轮次（此时才可沿用旧值并注明）。

### 2026-08-24 · 预算类缺口按「单步层 vs 会话层」分层核对
- 情境：核验 agent-loop 预算时发现 `DEFAULT_MAX_PARALLEL_TOOL_CALLS=10`（单步并行上限）与 `maxTokens`（单步输出上限）都已存在，差点误判「预算已覆盖」；实际 while 循环（agent.ts L199/L212/L263/L339）无任何会话级步骤上限。
- 教训：预算/上限类缺口必须分层列清单步层（并行/输出/单请求）与会话层（步骤/累计 token/成本）分别核对——单步上限存在 ≠ 会话级存在；每层给出行级证据（本缺口=018 步骤预算，与 016 token/成本预算同族不同维度）。
- 适用：性能/预算/稳定性类立项核验；不适用于无分层语义的全新能力立项。

### 2026-08-24 · 与已沉淀原则冲突的新候选直接拒绝，不重复评估
- 情境：StackOne Defender（22MB 提示注入检测模型，89% 准确率）表面满足「安全加固」；但第一轮已确立「检测型防御可被自适应攻击绕过，架构性分隔才是主控」（The Attacker Moves Second），且引入新依赖违反「禁止未审查依赖」护栏，与 003/006/009 架构级条目重叠。
- 教训：新候选与 MEMORY/STATE 已确立原则冲突时，按原则直接拒绝并在 BACKLOG 记录理由（状态=rejected），不重复完整评估流程——避免每轮被同类「检测型防御」候选反复消耗；拒绝记录本身就是可审查证据。
- 适用：安全类候选的快速过滤；不适用于原则尚未覆盖的新领域候选（仍需完整四问评估）。

### 2026-08-26 · 落地形态设计先查官方 spec 语义，再对照社区建议
- 情境：第七轮为 009/010 落地评审补方案时，读到官方 MCP Client Best Practices（2026-07-28）、官方 Tool Annotations blog（2026-03-16）与 DigitalApplied 审计 taxonomy——官方把远端 description 视为不可信输入、把 annotations 定义为「hint」（客户端 MUST 默认不可信，安全保证放确定性控制）。
- 教训：官方 spec 语义是落地形态的权威锚点，能避免在「社区完整形态（re-prompt 用户，触受保护路径）」与「最小安全子集（指纹+变更日志）」之间做无依据的选择——官方文档直接支持后者为 spec 合规基线，前者仅是可选 UX；设计安全条目的落地形态时先查官方规范原文。
- 适用：所有安全类/协议类条目的落地形态设计；不适用于纯内部进程改进（无外部规范可查）。

### 2026-08-26 · 跨环境恢复：进化状态只存于 fork 分支，重克隆后先恢复再续跑
- 情境：第七轮发现本地 master 已被重置/重克隆为 origin/master（b150a551b8，与上游完全一致），`.agents/evolution/` 与 `dsh-self-evolve` 技能缺失，全部进化历史仅存在于 fork `evolve/state`（且领先本地 master）。
- 教训：状态文件是唯一持久真相，运行前先 `git ls-remote fork evolve/state` 确认存在，用 `git checkout fork/evolve/state -- .agents/evolution/ .agents/skills/dsh-self-evolve/` 恢复后再续跑（blob 哈希校验与 fork 一致）；fork 分支领先本地 master 时推送必然非快进——推送前先 `gh pr list --head nightq:evolve/state` 确认无现存 PR，再按协议删分支重推（内容经状态文件完整保留，历史重写安全）。
- 适用：状态发布链路、环境迁移/重克隆/换机场景；不适用于同一环境连续运行的轮次（无需恢复步骤）。

### 2026-08-26 · 区分「真在途工作」与「工具会话产物」，后者入 .gitignore
- 情境：第七轮在途从 109 项缩至 6 项，其中 `.dsh-pilot/`（截图/下载）与 `.dsh-uploads/`（上传文件）是 harness 自身会话产物而非用户代码——它们持续污染 git status，反复触发研究模式降级误判。
- 教训：工作区状态判断与 RUNLOG 在途清单要分类标注「用户在途工作 vs 工具产物」；工具产物（截图/下载/上传缓存）应经 BACKLOG 条目（020）纳入 .gitignore，避免长期污染 status 与状态发布检查；无法改动时在 RUNLOG 明示类别。
- 适用：工作区状态判断、RUNLOG 在途清单记录；不适用于完整模式（工作区干净时无此问题）。

### 2026-08-27 · 研究模式跑只读门禁采集基线 = 把抽象条目变成具体修复清单
- 情境：第八轮在 001（hygiene 基线）落地前，先在研究模式运行 `pnpm run hygiene` 实测基线（运行前后对比 `git status --porcelain` 确认无新文件）——结果 11/13 绿、2 失败，每个失败都定位到根因与修复动作（constraints→`pnpm run clean` 清理 refactor 残留；vendor rescope→更新 rescope-vendor.ts 两处期望片段）。
- 教训：研究模式虽禁代码改动，但运行不改源码的只读检查门禁是合法且高价值的弱点采集——基线数据把「落地 001」从抽象任务变成「修复 2 个漂移」的具体清单，完整模式一启动即可直接执行；检查命令若产生文件则仅记录不落地。
- 适用：所有「先落地后验证」类条目的预研（001/007/011 等）；不适用于需要网络/key 的门禁（test:e2e、snapshot:record）。

### 2026-08-27 · hygiene 门禁失败根因多为「重构残留 + 检查脚本期望漂移」
- 情境：hygiene 的 constraints 失败=`packages/client/schema-form`、`web-react` 空壳残留（refactor(client) 合并后 lib/node_modules 未清理，无 package.json）；vendor rescope 失败=`knip.json` 的 `packages/util/home` 块被上游更新移走（moved）+ 中文文档链接修复成 `../rescope.zh.md` 后检查脚本仍期望 `../rescope.md`（partial）。
- 教训：这类漂移是「高质量」杠杆的真实信号——重构 PR 合并后应跑 `pnpm run clean` + `pnpm run hygiene` 验证；rescope/检查脚本的期望片段会随仓库结构漂移，hygiene 基线能系统抓住它们；修复=更新期望片段对照当前文件事实（而非改文件迁就脚本）。
- 适用：001 落地、重构后验证、vendor 同步轮次；不适用于无漂移语义的全新代码审计。

### 2026-08-27 · 并发实例检测：状态文件被并行写入时先核对再收敛
- 情境：第八轮与每日 08:05 定时实例并行运行同一 checkout——对方先完成提交（reflog 显示 08:05:38 commit `12d9b57eb0`）并推送 fork；我方编辑状态文件时收到「file changed since it was read」，经 reflog/文件 mtime 核实为另一实例所为，且其内容与我方独立发现高度一致（hygiene 11/13、同样 2 失败与修复配方、在途 6→7、漂移 ahead=1/behind=0）。
- 教训：编辑状态文件报「file changed」时先查 `git reflog` 与文件 mtime 判断是否并行实例而非自身失误；若对方已完整提交推送且结论一致，只做补充性收敛（缺失事实/CI 归因/并发记录），不重复整轮内容；并行跑同一轮会互相踩状态文件（last-writer-wins），排程上应避免同日多实例；双方独立复现同一结果是高置信度交叉验证。
- 适用：定时自动化与手动会话并存的场景；不适用于单实例连续运行（无并发写入）。

### 2026-08-28 · 上游大版本会过期本地「已就绪」的修复清单，落地前必须跨基线复核
- 情境：第八轮 001 修复清单（更新 rescope-vendor.ts 两处期望片段）已实测就绪；第九轮 fetch 发现上游发布 0.1.2-alpha.1（1079 提交），`git log b150a551b8..origin/master -- <清单涉及文件>` 显示上游已自行修复这两处期望（删旧 ExactEdit + 更新 zh 链接期望）——修复清单从「两处脚本改动 + clean」收窄为「仅 clean」。
- 教训：修复清单与审计结论都是时效性产物；工作区长时间在途（跨版本）时，落地前先核对上游是否已动过清单涉及文件（`git log <旧基线>..origin/master -- <文件>`），避免机械执行已过时的修复、或重复上游已完成的工作；「上游已修复」≠「本地自动拿到」，仍要 rebase + 重跑门禁验证。
- 适用：所有带具体修复步骤的 BACKLOG 条目（001/011 等）、跨版本落地的预研；不适用于单轮内即刻落地的条目（清单未过时）。

### 2026-08-28 · 漂移剧变是上游大版本信号：先查落点文件再判定缺口是否跨版本成立
- 情境：behind 从 0 突增至 1079，origin 发布 0.1.2-alpha.1（agent-presets 迁移、top-level examples 退役等大规模重构）；逐文件核对后确认——009 tools.ts 证据行未漂移（L166 透传仍在）、010 connection.ts 上游 0 提交、018 agent.ts while(true) 仍在且无步骤上限 → 三个审计结论跨版本全部成立，而 001 的 rescope 期望恰好被重构「顺带修复」。
- 教训：漂移剧变时不要只记数字，用 `git log <旧基线>..origin/master -- <落点文件>` + `git show origin/master:<文件> | grep <证据行>` 把每个待落地/待评审条目的落点文件过一遍，区分「缺口已修复（条目可关闭或降级）」与「缺口仍在（结论跨版本有效）」；`git show <ref>:<path>` 不 checkout、不污染脏工作区，是研究模式的合法跨版本核验手段。
- 适用：上游大版本发布后的审计/落地预研；不适用于无落点文件的进程级条目。

### 2026-08-28 · MCP 工具投毒「结构性根因」权威：协议无数据/指令边界，客户端策展是唯一能力范围内防御
- 情境：第九轮为 009/010 评审补权威，Speakeasy（2026）明确「There is no boundary in the protocol that marks a tool description as data rather than instructions」——MCP 协议层根本没有把描述标记为数据的边界，因此「客户端侧策展」（描述来源标注/指令隔离=009）不是可选增强而是唯一可行的防御面；「version pinning by hash」使 rug pull 变更指纹即被拒=010 指纹对比的业界标准形态；「Model-layer defenses miss it; the MCP gateway is where it stops」=harness 层（本仓库 mcp-client）是天然拦截点。
- 教训：评估「是否值得做」时，结构性根因（协议缺陷）+ 网关层落点（harness 可改）+ 业界标准防御形态（哈希钉扎）三要素齐备的条目应稳定升级为高优先级安全提案；这类权威对既有审计是「确认」而非「新发现」，应回填到对应 BACKLOG 条目的落地记录而非新开条目。
- 适用：MCP/工具信任边界类安全条目的评审与优先级调整；不适用于无外部协议可查的内部进程改进。
